# ADR-022. Pruebas del frontend con Vitest, Testing Library, jsdom y axe-core

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado |
| Contexto | El Plan de Calidad fija Vitest y Testing Library para las pruebas de componentes del frontend y deja sus versiones para cuando se incorporen en la Etapa 2. HU-001 es la primera historia que lo necesita: su criterio CA-HU-001-02 pide que la página se use por completo con teclado y sin errores graves de accesibilidad. Playwright, con axe integrado, llega en la Etapa 4, así que hasta entonces la revisión de accesibilidad tiene que correr en las pruebas de componentes. |
| Drivers | DRV-010 |
| Alternativas | Navegador simulado: jsdom o happy-dom. Revisión de accesibilidad: axe-core llamado directamente, vitest-axe o esperar a Playwright. |
| Decisión | Vitest 5.0.5 con jsdom 30.1.3, configurado en `vite.config.ts` para reutilizar la configuración de Vite. Testing Library: `@testing-library/react` 16.3.3, `@testing-library/dom` 10.4.2, `@testing-library/user-event` 14.6.8 y `@testing-library/jest-dom` 7.0.1. axe-core 4.14.0 llamado desde `src/test/axe.ts`, que devuelve solo las fallas de impacto serio o crítico; la regla de contraste se desactiva porque jsdom no calcula colores, y el contraste queda validado en la sección 12.3 del documento de Diseño. Las pruebas viven junto al archivo que prueban (`HomePage.test.tsx`) y montan las mismas rutas de producción con `renderRoute`. Se ejecutan con `pnpm test`, también en la CI. |
| Justificación | Vitest comparte la configuración y los plugins de Vite, así que no hay una segunda forma de compilar el código. jsdom es el entorno más completo y el que Testing Library documenta como referencia. axe-core es el motor que usará Playwright en la Etapa 4, de modo que las reglas no cambian; vitest-axe no publica versiones desde 2022. |
| Consecuencias positivas | Cada historia del frontend entrega pruebas de sus criterios en la misma rama. La accesibilidad básica se revisa en cada pull request desde ahora y no desde la Etapa 4. |
| Consecuencias negativas | jsdom no implementa `showModal` de `<dialog>` ni resuelve URL relativas en `fetch`; `src/test/setup.ts` agrega un reemplazo mínimo del diálogo y una URL base para el cliente generado. jsdom no aplica estilos, así que el diseño visual y el contraste se revisan en el navegador. |
| Riesgos | Que el reemplazo de `<dialog>` oculte una diferencia con el navegador real: lo cubren las pruebas de punta a punta con Playwright en la Etapa 4. |
| Fecha y responsables | 01/11/2026, Juan Diego Acevedo Calderon |
| Decisión que reemplaza / es reemplazada por | Ninguna. |
