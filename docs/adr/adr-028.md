# ADR-028. Sesiones comprobadas en cada petición y protección contra CSRF

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado |
| Contexto | HU-007 abre las primeras sesiones de ALETHEIA. ADR-007 fijó un JWT de acceso de 10 minutos y un token de renovación de 14 días en cookies, pero no dijo cómo se cortan esas sesiones antes de que el JWT venza, y CA-HU-009-03 exige que cerrar todas las sesiones invalide las de otros dispositivos de inmediato. Además, al viajar la sesión en cookies, toda petición que cambia algo queda expuesta a que otro sitio la provoque (CSRF), y la especificación pide tres barreras: SameSite=Strict, la verificación de Origin y un encabezado propio obligatorio. |
| Drivers | DRV-004, DRV-007 |
| Alternativas | Un JWT que nadie revisa durante sus 10 minutos, que deja una sesión cerrada viva hasta que vence; una lista de tokens revocados en memoria, que se pierde al reiniciar y no se comparte con otro proceso; sesiones de servidor sin JWT, que contradicen ADR-007; un token CSRF sincronizado en un formulario, innecesario cuando la interfaz y la API comparten origen y ya existe el encabezado propio. |
| Decisión | El token de acceso es un JWT HS256 firmado con la subclave `aletheia:session:access`, derivada de la misma clave maestra de ADR-027, con `aud=session`, `sub` (la persona) y `sid` (la familia de la sesión). El token de renovación son 32 bytes aleatorios, y `refresh_tokens` guarda solo su SHA-256. Todas las renovaciones de un ingreso comparten familia y vencimiento absoluto de 14 días. En cada petición protegida, la dependencia `get_principal` valida el JWT y comprueba con una sola consulta que la persona esté activa y que su familia tenga un token sin revocar y sin vencer; después fija el contexto de su organización para Row-Level Security. Las cookies son `__Host-aletheia_access` (ruta `/`, 10 minutos) y `__Secure-aletheia_refresh` (ruta `/api/v1/auth`, hasta el vencimiento de la familia), ambas HttpOnly, Secure y SameSite=Strict. Contra CSRF, `SameOriginMiddleware` rechaza con 403 todo POST, PUT, PATCH o DELETE bajo `/api` que no lleve `X-Aletheia-Request: 1`, o cuyo `Origin` o `Sec-Fetch-Site` digan que viene de otro sitio. CORS permite solo el origen del sitio. |
| Justificación | Revisar la familia en cada petición cuesta una consulta indexada y hace que bloquear una cuenta, cerrar todas las sesiones o detectar un token robado surta efecto en la siguiente petición. Las subclaves impiden que un enlace de correo sirva como acceso o al revés. El prefijo `__Host-` obliga al navegador a rechazar la cookie si no es Secure, si trae dominio o si su ruta no es `/`, así que ningún subdominio puede plantar una propia; la ruta de la cookie de renovación hace que solo viaje a las rutas que la usan. Un formulario de otro sitio no puede poner un encabezado propio, y un script de otro sitio solo podría con un permiso de CORS que la API nunca da. |
| Consecuencias positivas | La revocación es inmediata y verificable con pruebas. La base solo guarda hashes: una copia de `refresh_tokens` no abre ninguna sesión. El ingreso no revela qué correos existen: un correo sin cuenta pasa por un hash señuelo de Argon2id con los mismos parámetros, recibe el mismo mensaje y cuenta igual para el límite de intentos (RN-026). |
| Consecuencias negativas | Cada petición protegida hace una consulta más. Rotar la clave maestra cierra todas las sesiones a la vez, además de invalidar los enlaces pendientes. Todo cliente que cambie algo en la API debe enviar el encabezado propio; la interfaz lo envía siempre desde `src/api/runtimeConfig.ts`. |
| Riesgos | Un XSS en la propia interfaz podría hacer peticiones con la sesión de la persona; lo mitigan la CSP estricta de Caddy y que React no inserta HTML crudo. La rotación del token de renovación y la detección de reutilización llegan con HU-009 sobre estas mismas familias. |
| Fecha y responsables | 05/11/2026, Juan Diego Acevedo Calderon |
| Decisión que reemplaza / es reemplazada por | Ninguna. Precisa ADR-007 y extiende ADR-027. |
