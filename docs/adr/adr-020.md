# ADR-020. Contrato guardado en el repositorio y cliente generado con Hey API

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado |
| Contexto | ADR-008 definió que el frontend genera sus tipos y su cliente desde el OpenAPI de FastAPI, y dejó para TT-009 la elección de la herramienta. Además, FastAPI documentaba los 422 con su propio esquema (`HTTPValidationError`), mientras la API responde con Problem Details; un cliente generado así tendría tipos de error que nunca llegan. El frontend usa TypeScript 6.0 y ADR-019 exige que la CI no acepte dependencias con avisos de seguridad. |
| Drivers | DRV-010 |
| Alternativas | openapi-typescript con openapi-fetch; Hey API (`@hey-api/openapi-ts`) con su cliente fetch; tipos escritos a mano. |
| Decisión | El backend exporta el contrato a `backend/openapi.json` con `uv run python -m app.contract`, sin configuración ni base de datos, y el archivo se guarda en el repositorio. En el contrato, toda respuesta 4xx o 5xx es `application/problem+json`: `ValidationProblem` en los 422 y `Problem` en el resto, y cada operación se identifica con el nombre de su función. El frontend genera tipos, cliente y una función por operación con `@hey-api/openapi-ts` 0.99.0 en `src/api/generated`, formateados con Prettier; el cliente se genera dentro del proyecto y no agrega dependencias de ejecución. Una prueba del backend falla si el contrato guardado no coincide con la API o si su versión no es la del proyecto, y la CI regenera el cliente y falla si cambia algo. |
| Justificación | openapi-typescript 7.13.0 declara solo TypeScript 5, no publica versiones desde febrero de 2026 y su dependencia minimatch tiene un aviso de seguridad cuya corrección aún no cumple la espera de ADR-019. Hey API declara compatibilidad con TypeScript 6 y se publica con frecuencia; su único aviso, en js-yaml 4.2.0, se corrige forzando js-yaml 4.3.2, que cumple la espera. Guardar el contrato permite ver en cada pull request cómo cambia la API y generar el cliente sin levantar el backend. |
| Consecuencias positivas | Un cambio en la API que no se refleja en el frontend no llega a develop. Los errores tienen en el frontend el mismo tipo que la API responde. Las versiones de la API se mantienen alineadas: la prueba avisa si `backend/app/main.py` y `pyproject.toml` difieren. |
| Consecuencias negativas | Cada cambio de API exige regenerar dos archivos. Hey API sigue en versiones 0.x: una actualización puede cambiar el código generado, y ese pull request debe incluirlo regenerado. Se mantiene un override de js-yaml en `pnpm-workspace.yaml` hasta que Hey API traiga una versión corregida. |
| Riesgos | Que alguien edite a mano el código generado: la CI lo detecta. Que Hey API cambie su configuración entre versiones 0.x: la versión va fija y se revisa en cada pull request de Dependabot. |
| Fecha y responsables | 31/10/2026, Juan Diego Acevedo Calderon |
| Decisión que reemplaza / es reemplazada por | Ninguna; completa ADR-008. |
