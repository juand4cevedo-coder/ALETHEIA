# ADR-037. Hash de custodia calculado por la base, verificador independiente y anclaje externo

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado |
| Contexto | ADR-004 encadena los eventos de custodia, pero el trigger `custody_events_chain` solo comprobaba el número del evento y el hash anterior: aceptaba el `event_hash` que mandara la aplicación sin comprobar que correspondiera a los datos guardados. La base garantizaba que la cadena no tuviera huecos, pero no que cada hash fuera el de su evento. Además, una cadena guardada en la misma base que protege no prueba nada frente a quien controle esa base. |
| Drivers | DRV-001, DRV-004 |
| Alternativas | Que la aplicación calcule el hash y la base lo compruebe; que lo calcule solo la base y nadie lo repita; firmar cada evento con una llave de la aplicación; anclar cada evento en una autoridad externa. |
| Decisión | La base calcula el hash al insertar (migración 0013): SHA-256 sobre `custody_event_canonical`, la serialización canónica versión 1 (`aletheia-custody-v1`), con un campo por línea en orden fijo (hash anterior en hexadecimal, caso, número, evidencia, actor, acción, fecha en UTC con microsegundos y `details` en el texto canónico de JSONB, al final). Cualquier valor que mande la aplicación se descarta. `app.services.custody_chain` repite el cálculo con `hashlib`, sin usar ninguna función de la base, y verifica la secuencia, el hash anterior y el hash propio de cada evento; su informe da el primer evento que no cierra y el hash de la cabeza. Una prueba compara la serialización de la base con la de Python en cada tipo de dato. El anclaje externo queda decidido así: el hash de la cabeza de cada caso se sella con la autoridad RFC 3161 de ADR-015 al exportar el paquete y, después, una vez al día si la cadena cambió. El token se guarda con el número del evento que cubre y va en el paquete de preservación, para que un tercero compruebe la cadena sin confiar en ALETHEIA. Se construye con HU-020 y HU-025. |
| Justificación | Si la base calcula el hash, ningún error de la aplicación puede guardar un evento con un hash que no le corresponda. Que un verificador independiente lo repita permite detectar una alteración hecha con acceso directo a la base, incluso saltándose los triggers, y que el mismo cálculo se haga fuera de ALETHEIA con los datos del paquete. El sello externo de la cabeza fija en el tiempo el estado de la cadena: después de sellada, reescribirla entera ya no pasa inadvertida. Usa la autoridad que el producto ya necesita, sin un servicio nuevo. |
| Consecuencias positivas | La integridad de cada evento queda garantizada por construcción y comprobable desde fuera. HU-024 (verificar la cadena) y el paquete de HU-025 usan el mismo verificador. |
| Consecuencias negativas | Cambiar la serialización exige una versión nueva y conservar la anterior para verificar los eventos viejos. Mientras no exista el anclaje, quien controle la base puede reescribir una cadena completa sin que el verificador lo note. |
| Riesgos | Que la serialización de Python se separe de la de PostgreSQL; lo impide la prueba que las compara. Que la autoridad de sellado no responda; el anclaje queda pendiente y se reintenta como cualquier tarea (ADR-038). |
| Fecha y responsables | 10/11/2026, Juan Diego Acevedo Calderon |
| Decisión que reemplaza / es reemplazada por | Complementa ADR-004 y ADR-015. |
