# ADR-027. Enlaces firmados de un solo uso

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado |
| Contexto | HU-006 necesita un enlace en el correo que demuestre que la persona controla su dirección, y la recuperación de la contraseña tendrá la misma necesidad. Cada enlace debe vencer, servir para una sola cosa, usarse una sola vez y no quedar expuesto en registros ni en el historial del navegador, sin sumar tablas ni servicios que un solo desarrollador tenga que mantener. |
| Drivers | DRV-007, DRV-008 |
| Alternativas | Un token aleatorio cuyo hash se guarda en una tabla con su vencimiento y la marca de usado; un JWT firmado sin nada que lo invalide después de usarlo; una sola clave para todos los usos; el token en la consulta de la dirección (`?t=`) en lugar del fragmento. |
| Decisión | Cada enlace es un JWT HS256 firmado con PyJWT. La clave maestra vive en Parameter Store (`/aletheia/prod/app/token-signing-key`) y de ella se deriva con HMAC-SHA256 una subclave por uso (`aletheia:link:<uso>`); el uso también va en `aud`. El token lleva `iss`, `aud`, `sub` con el UUID de la persona, `iat`, `exp` y `st`, el sello del estado: un HMAC del dato que el uso cambia, que en la verificación es el correo todavía sin verificar. Al recibirlo, la API comprueba firma, emisor, uso y vigencia, bloquea la fila de la persona y compara el sello con el estado actual. El enlace lleva el token en el fragmento (`/verificar-correo#t=...`); la página lo borra de la dirección y lo envía una sola vez a `POST /api/v1/auth/verify-email`. |
| Justificación | El sello vuelve de un solo uso a un token que no se guarda en ninguna parte: el mismo cambio que produce el enlace, como verificar el correo o cambiar la contraseña, lo deja sin valor. Las subclaves impiden que un token de un uso valide en otro aunque salgan del mismo secreto. El sello es un HMAC y no un SHA-256 simple porque el token se puede leer, y un SHA-256 del correo se podría comparar contra listas de correos conocidos. El navegador nunca envía el fragmento al servidor, así que el token no queda en los registros de Caddy ni en la cabecera Referer. |
| Consecuencias positivas | No hay tablas ni tareas de limpieza para los enlaces. La recuperación de la contraseña usa el mismo módulo (`app.core.tokens`) y sella el `security_stamp` de la cuenta (ADR-034). Las invitaciones no usan este mecanismo: necesitan listarse y revocarse una por una, así que viven en la tabla `invitations` con un token opaco guardado como hash (ADR-035). Todas las fallas dan el mismo error, sea un enlace alterado, vencido, de otro uso o ya usado, así que quien prueba enlaces no aprende nada. |
| Consecuencias negativas | No existe una lista de enlaces emitidos, y uno solo no se puede revocar sin cambiar el estado que sella. Rotar la clave maestra invalida todos los enlaces pendientes y, desde HU-007, también las sesiones, que derivan su subclave de la misma clave. El contenido del token es legible, por eso solo lleva el UUID y el sello. |
| Riesgos | Que se filtre la clave maestra y alguien firme sus propios enlaces. En producción solo la lee el rol de la instancia, como SecureString, y nunca llega en una variable de entorno. Ante una sospecha se crea una versión nueva del parámetro y se reinician la API y el trabajador. El abuso del endpoint se frena con el límite `email_verification_ip`, de 20 intentos por dirección IP cada 15 minutos, y con el tope de 1024 caracteres por token. |
| Fecha y responsables | 05/11/2026, Juan Diego Acevedo Calderon |
| Decisión que reemplaza / es reemplazada por | Ninguna. Complementa ADR-007. ADR-034 la aplica a la recuperación y ADR-035 deja las invitaciones fuera de ella (corrección del 07/11/2026). |
