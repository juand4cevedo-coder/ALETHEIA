# ADR-039. Alcance de Row-Level Security y autorización dentro de las funciones privilegiadas

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado |
| Contexto | ADR-006 aísla las organizaciones con filtros en el código y Row-Level Security. Las políticas comparan cada fila con `aletheia.organization_id` y `aletheia.user_id`, valores de sesión que la aplicación fija con `set_config` y que el rol `aletheia_app` puede cambiar. Hay que dejar claro qué protege eso y qué no. Además, `purge_case` corre como dueño del esquema, sin pasar por las políticas, y no comprobaba que quien pide la eliminación fuera la persona de la sesión ni que tuviera permiso para hacerlo. |
| Drivers | DRV-002, DRV-004 |
| Alternativas | Un rol de base por organización; fijar el contexto con una función que verifique una firma; confiar en que la aplicación autorice antes de llamar a las funciones privilegiadas. |
| Decisión | Row-Level Security se documenta como **aislamiento lógico**: protege de una consulta mal escrita, de un filtro olvidado o de un identificador manipulado en una petición, porque la sesión solo tiene el contexto que fija `authenticate`. **No es una frontera** frente a quien tenga las credenciales de `aletheia_app`: esa persona puede fijar cualquier contexto y leer cualquier organización. Contra ese caso valen otras barreras: la contraseña de la base vive como SecureString en Parameter Store y solo la lee el rol de la instancia; `aletheia_app` no puede editar ni borrar la custodia, las constancias ni las evidencias; la base calcula los hashes de custodia y un verificador independiente detecta alteraciones (ADR-037); y el anclaje externo deja evidencia fuera de la base. Toda función `SECURITY DEFINER` comprueba ella misma la autorización: desde la migración 0013, `purge_case` exige que `p_requested_by` sea la persona de la sesión y que tenga el rol de propietario o administrador en la organización del caso, además de que el caso sea de esa organización y esté marcado para eliminar. El servicio que la llame (HU-034) aplicará también sus propias reglas antes de llamarla. `invitation_for_token` solo devuelve identificadores y no cambia nada. |
| Justificación | Llamar frontera a algo que no lo es lleva a decisiones de seguridad equivocadas. Separar el aislamiento lógico de la protección ante credenciales robadas obliga a poner controles reales para lo segundo. Que cada función privilegiada se autorice sola evita que un error de la aplicación, o una llamada directa, la use para lo que no debe. |
| Consecuencias positivas | El modelo de amenazas queda escrito y coincide con lo que la base hace. `purge_case` ya no borra un caso a nombre de otra persona ni de un rol sin permiso. |
| Consecuencias negativas | La autorización de las funciones privilegiadas se duplica: en el servicio y en la base. |
| Riesgos | Que se filtren las credenciales de `aletheia_app`; se rotan creando una versión nueva del parámetro, y la detección depende del verificador y del anclaje. |
| Fecha y responsables | 10/11/2026, Juan Diego Acevedo Calderon |
| Decisión que reemplaza / es reemplazada por | Precisa el alcance de ADR-006 y endurece ADR-004. |
