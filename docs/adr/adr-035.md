# ADR-035. Invitaciones con token opaco guardado como hash

| Campo | Contenido |
| --- | --- |
| Estado | Aceptado |
| Contexto | HU-011 envía por correo una invitación de un solo uso que vence a las 72 horas y ocupa un cupo del plan mientras siga abierta (RN-012). Quien administra la oficina necesita ver las invitaciones pendientes y revocar una antes de que la acepten (FLU-003, A2). ADR-027 anticipaba que las invitaciones usarían el mismo enlace firmado sin tabla que la verificación del correo, pero el diccionario de datos ya define la tabla `invitations` (DAT-07) con `token_hash`, vencimiento, aceptación y revocación. |
| Drivers | DRV-004, DRV-007, DRV-008 |
| Alternativas | Un JWT firmado y sellado con el estado de la invitación, como en ADR-027, sin guardar el token; un token aleatorio guardado en claro; generar el token al crear la invitación y ponerlo en el payload de la tarea de correo; contar solo los miembros para el cupo, sin las invitaciones abiertas. |
| Decisión | Se conserva la tabla de DAT-07. El enlace lleva un token opaco de 32 bytes aleatorios (`app.core.tokens.new_opaque_token`) y la base guarda solo su SHA-256 en `token_hash`, igual que los tokens de renovación. Al crear la invitación, `token_hash` recibe el hash de un valor que se descarta; el token real se genera en el trabajador justo antes de enviar el correo, que reemplaza el hash en la misma transacción. La tarea de la cola lleva solo `invitation_id` y `organization_id`. El enlace va en el fragmento (`/invitacion#t=...`). Invitar bloquea la fila de la organización y cuenta como cupo usado los miembros más las invitaciones abiertas (ni aceptadas, ni revocadas, ni vencidas); el plan Firma, que admite usuarios adicionales, no tiene tope. Revocar fija `revoked_at`. Crear y revocar quedan en la auditoría (`invitation_sent`, `invitation_revoked`), y cada cuenta puede enviar hasta 20 invitaciones cada 15 minutos (`invitation_account`). La migración 0011 agrega el índice parcial de las invitaciones abiertas. |
| Justificación | Una invitación es un objeto que se lista y se revoca una por una, y eso exige una fila; con un JWT sin tabla, revocar una sola invitación no tendría qué estado cambiar. El token es aleatorio, así que un SHA-256 sin sal basta y una copia de la base no sirve para aceptar invitaciones. Generar el token al enviar evita que exista en la cola, en los registros o en la base: si la tarea se reintenta, el token cambia y solo el último correo sirve. Bloquear la organización impide que dos invitaciones simultáneas ocupen a la vez el último cupo, y contar las abiertas impide invitar más personas de las que el plan admite. |
| Consecuencias positivas | La interfaz muestra las pendientes con su vencimiento y las revoca. Una invitación revocada o vencida libera su cupo. La aceptación (HU-012) busca la invitación por el hash del token con una función propia de PostgreSQL, sin conocer antes la organización. |
| Consecuencias negativas | Un reintento de la tarea invalida el enlace del intento anterior. Desde ADR-038 el hash se confirma antes de enviar, así que el enlace que llega siempre sirve. |
| Riesgos | Que alguien use ALETHEIA para enviar correos a direcciones ajenas: lo limitan el cupo del plan, que en la prueba gratis no deja invitar, y el tope por cuenta. Que el correo llegue a quien no es: solo sirve durante 72 horas y quien administra puede revocarlo. |
| Fecha y responsables | 07/11/2026, Juan Diego Acevedo Calderon |
| Decisión que reemplaza / es reemplazada por | Corrige lo que ADR-027 anticipaba para las invitaciones; los enlaces de la cuenta siguen con ADR-027. |
